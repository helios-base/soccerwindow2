- ベースブランチ: `develop`
- 作業ブランチ: `feature/ubuntu-26.04`（ユーザが GitHub 上で develop から作る）
- 関連する計画書

  - librcsc の `docs/plan/2026-11-21_boost-cmake-maintenance.md`（librcsc リポジトリ。PR #119 で develop にマージ済み（`897bc90`）。その Phase 8 が、この計画で行う soccerwindow2 側の作業）

## 1. 背景と目的

soccerwindow2 の Qt6 対応の作業中（2026-11-20）に、CI に Ubuntu 26.04 を試験的に加えたところ、librcsc の configure が `Could not find a version of the Boost::System library!` で失敗した。Boost 1.89 で Boost.System のライブラリが廃止されたのに、librcsc がそれを要求していたためで、Ubuntu 26.04 は CI から外した。

その後、librcsc で次の対応が行われ、develop にマージされた（PR #119）。

- Boost.System への依存を除き、Boost 1.70 以上のヘッダだけを使うようにした。公開ヘッダから Boost の読み込みを除いた（利用側に Boost を要求しなくなった）。
- GCC 15 でのビルドエラーを直した（`<algorithm>` の読み込み漏れなど）。Ubuntu 24.04・26.04 の CI で、CMake と Autotools の両方のビルドとテストが通る。
- CMake のビルドを直し、CMake をメインのビルドシステムにした。既定のインストール先を `~/.local` にし、CMake のパッケージ設定ファイル `librcscConfig.cmake`（`find_package(librcsc CONFIG)`、インポートターゲット `librcsc::rcsc`）をインストールするようにした（CMake でインストールしたときだけ）。
- CI と文書の対象を Ubuntu 24.04・26.04 にした（22.04 は外した）。

これを受けて、soccerwindow2 でも次のことを行う。

1. Ubuntu 26.04（GCC 15、Qt 5.15.18 / 6.10.2、Boost 1.90、CMake 4.x）で、CMake と Autotools のどちらでもビルドとテストができるようにし、CI の対象に戻す。
2. librcsc が提供する `librcscConfig.cmake` を使って librcsc を探すようにする。Autotools でインストールされた librcsc（Config がない）のために、今の `cmake/FindLibrcsc.cmake` も予備として残す。
3. CI での librcsc のビルドを、CMake のジョブでは librcsc のメインになった CMake にする（Autotools のジョブは Autotools のまま）。
4. librcsc の既定のインストール先の変更（`~/.local`）に合わせて、Autotools の librcsc の探し方を見直す。
5. librcsc の公開ヘッダが Boost を読み込まなくなったので、soccerwindow2 の Boost への依存をなくす。
6. librcsc に合わせて、Ubuntu 22.04 を CI と文書の対象から外す。
7. 文書（`README.md`、`docs/build.md`）とリリースノートを現状に合わせる。

## 2. 現状の調査結果（2026-11-23、develop の `1df28c1`）

### 2.1 CI（`.github/workflows/build.yml`）

- 対象: Ubuntu 22.04・24.04 × Qt5・Qt6 × CMake・Autotools の8ジョブ。
- Ubuntu 22.04 の Autotools のジョブでは Qt WebSockets を入れず、WebSocket の接続なしのビルドを確かめている（`test/check_websocket.sh`）。ほかのジョブでは Qt WebSockets を入れている。
- 共通のパッケージに、librcsc のための `libboost-system-dev` が入っている（Ubuntu 26.04 には、このパッケージがない見込み）。
- librcsc は、develop ブランチを Autotools でビルドして `~/local` にインストールし、`git ls-remote` で得たリビジョンをキーにしてキャッシュしている。コメントには「librcsc の CMake ビルドはメンテナンスされていない」と書いてある（今は解消済み）。
- 使っているアクションは `actions/checkout@v4`・`actions/cache@v4`・`actions/upload-artifact@v4`（Node.js 20 で動く版）。librcsc の CI では、Node.js 20 の非推奨の警告が出たため、`actions/checkout@v7`・`actions/upload-artifact@v7`・`actions/download-artifact@v8` に更新している。

### 2.2 librcsc の探し方

- CMake（`cmake/FindLibrcsc.cmake`）: `find_path`・`find_library` で探し、インポートターゲット `Librcsc::Librcsc` を作る。ヒントはキャッシュ変数 `LIBRCSC_INSTALL_DIR`（既定は `~/.local;~/local`）と環境変数 `LIBRCSC_PREFIX`。`librcscConfig.cmake` は使っていない。
  - `Librcsc::Librcsc` を使っているのは `src/model/CMakeLists.txt` だけ。ルートの `CMakeLists.txt` は `Librcsc_LIBRARY`・`Librcsc_INCLUDE_DIR` を構成時に表示している。
  - `distcheck`（`cmake/DistCheck.cmake`）は、外側の `LIBRCSC_INSTALL_DIR` と `CMAKE_PREFIX_PATH` を内側の configure に引き継ぐ。
- Autotools（`configure.ac`）: `--with-librcsc` がなければ、`$HOME/local`、`$HOME/.local`、`/opt/local`、`/usr/local`、`/usr` の順に探す。CMake・librcsc・helios-base は `~/.local` を先に探すので、順序が逆になっている。両方にあると古い `~/local` のものが使われる。
- librcsc の `librcscConfig.cmake` は、`librcsc::rcsc`（SHARED IMPORTED）を、インストール先からの相対パスで定義する。インクルードディレクトリは `<PREFIX>/include`、`cxx_std_17` を伝え、zlib・Boost は伝えない。バージョンは 2026 で、互換性は `AnyNewerVersion`。Autotools でインストールした librcsc には Config がない。

### 2.3 Boost

- soccerwindow2 自身が使っている Boost は、`src/model/csv_logger.h` の `boost::lexical_cast` だけ。`CSVLogger` はどこからも使われていない。ほかの Boost の読み込みは、librcsc の公開ヘッダ経由だったが、librcsc の公開ヘッダからは Boost の読み込みが除かれた。
- CMake は `find_package(Boost 1.41 REQUIRED)`（ポリシー CMP0167 を NEW にしている）、Autotools は `AX_BOOST_BASE([1.41.0])`。CMP0167 が NEW のとき（CMake 3.30 以降）は `BoostConfig.cmake` だけで探すため、実際には Boost 1.70 以上でないと見つからない。librcsc は最低バージョンを 1.70 に上げた。
- `soccerwindow2.spec.in` は `BuildRequires: boost-devel >= 1.41`。librcsc の要求は `librcsc >= 1.3.0`（今の librcsc のバージョンは 2026）のまま。

### 2.4 文書

- `README.md` と `docs/build.md` は、対象を Ubuntu 22.04・24.04 としている。
- `docs/build.md` の librcsc の節は、Autotools でのビルドと `libboost-system-dev` のインストールを案内している。
- `docs/build.md` の「Notes > Ubuntu 26.04」に、librcsc が Ubuntu 26.04 でビルドできないことが書いてある。
- `docs/build.md` の configure のオプションの表に、librcsc を探す順序（`~/local` が先）が書いてある。

### 2.5 Ubuntu 26.04 で予想される問題

2026-11-20 の試験的なジョブは librcsc の configure で止まったため、soccerwindow2 のビルドは Ubuntu 26.04 でまだ試していない。librcsc の CI で分かったことと合わせて、次の問題が予想される。

- GCC 15: 標準ライブラリのヘッダが、ほかのヘッダ（`<algorithm>` など）を読み込まなくなった。librcsc では `std::sort` などを使う26ファイルで読み込み漏れがあった。soccerwindow2 では Qt のヘッダ経由で読み込まれる所が多いと思われるが、Qt に依存しない `src/model` は漏れがあればエラーになる。
- Qt 6.10: 新たに非推奨になった API の警告が出る可能性がある（今は Qt 6.2〜6.4 で警告0件）。offscreen での GUI のテストの結果が変わる可能性もある。
- Qt5 の qmake: Autotools の Qt5 のジョブは、qtchooser の `/usr/bin/qmake` と `QT_SELECT=qt5` を前提にしている。Ubuntu 26.04 に qtchooser がない場合は、Qt の検出（`SW2_CHECK_QT`）が Qt5 の qmake を見つけられない可能性がある。
- パッケージ名: Qt・Qt WebSockets・OpenGL のパッケージ名が 24.04 と同じかを確かめる必要がある。
- Autoconf 2.72・CMake 4.x: 古いマクロや書き方の警告が出る可能性がある（CMake は `cmake_minimum_required(VERSION 3.16)` なので、CMake 4 の互換性の問題はない見込み）。

### 2.6 手元の環境

- Ubuntu 24.04（GCC 13.3、CMake 3.28.3、Qt 5.15.13 / 6.4.2、Boost 1.83）。
- librcsc は `~/.local` に CMake でインストールされている（`~/.local/lib/cmake/librcsc/` に Config がある。Release と Debug の両方の `librcscTargets-*.cmake` がある）。
- 計画の作成時には、`~/local/lib/cmake/librcsc/` に古い Config（2026-11-21 22:50）が残っていた。`~/local/lib` に librcsc のライブラリはないため、この Config が使われると、存在しないファイルを参照するエラーになる。ユーザが削除した（2026-11-23）。
- `docker` コマンドはあるが、ユーザが `docker` グループに入っていないため使えない（`permission denied`）。

## 3. 決定事項（2026-11-23、ユーザと決定）

| # | 項目 | 決定 |
|---|---|---|
| 1 | Ubuntu 22.04 | CI と文書の対象から外し、Ubuntu 24.04・26.04 にする（librcsc に合わせる）。CI は 24.04・26.04 × Qt5・Qt6 × CMake・Autotools の8ジョブ。librcsc の CI が 22.04 を確かめなくなったため、librcsc の変更で 22.04 のジョブだけが失敗するおそれがある。最低バージョン（Qt 5.15・6.2、CMake 3.16）は変えず、CI では確かめないことを文書に書く。今 22.04 の Autotools のジョブで行っている「Qt WebSockets なしのビルド」の確認は、24.04 の Autotools のジョブに移す（26.04 の Autotools のジョブでは Qt WebSockets ありを確かめる） |
| 2 | CI での librcsc のビルド方法 | soccerwindow2 と同じビルドシステムで librcsc をビルドする（CMake のジョブは CMake、Autotools のジョブは Autotools）。CMake のジョブでは Config で見つかることを確かめ、予備の `FindLibrcsc.cmake` での構成・ビルド・テストも追加で確かめる。Config を使う場合と、Autotools でインストールした librcsc を使う場合の両方を CI で確かめられる |
| 3 | librcsc を Config で探すときの扱い | Config（`find_package(librcsc CONFIG)`）を先に探し、なければ `FindLibrcsc.cmake` で探す。どちらの場合も、使うターゲットの名前を librcsc の `librcsc::rcsc` に揃える（`FindLibrcsc.cmake` が同じ名前のインポートターゲットを作る）。バージョンは指定しない。librcsc の計画書の Phase 8 と「3. 決定事項」（Config は CMake でインストールしたときだけ）に沿う |
| 4 | soccerwindow2 の Boost への依存 | 外す。`csv_logger.h` の `boost::lexical_cast` を標準ライブラリで置き換え、CMake・Autotools の Boost の検出、`m4/ax_boost_base.m4`、spec の `boost-devel` を削除する。librcsc の公開ヘッダが Boost を読み込まなくなったので、soccerwindow2 が Boost を使う所は、使われていない `CSVLogger` の1行だけになった。librcsc のビルドには Boost が要るので、文書の librcsc の手順には `libboost-dev` が残る |

| 6 | 作業ブランチ | `feature/ubuntu-26.04`（ユーザが GitHub 上で develop から作る） |

## 4. 実装計画

各フェーズを1つ以上のコミットにし、段階ごとにユーザが差分を確認してからコミットする（コミットは作業の種類ごとに分ける）。コミット前に、コミットメッセージ案と git コマンドを提示する。

フェーズの順序: Phase 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8。CI で Ubuntu 26.04 の問題を早く知るため、CI の変更（Phase 1）を最初に行う。

### Phase 0: 準備

- 本計画書を作成し、未決事項をユーザと決めて「3. 決定事項」にする。
- ユーザが作業ブランチ `feature/ubuntu-26.04` を GitHub 上で develop から作る。
- `~/local/lib/cmake/librcsc/` の古い Config の扱いをユーザに確認する（「2.6」）。→ ユーザが削除した。

### Phase 1: CI に Ubuntu 26.04 を加える

ここでは、librcsc のビルドは今のまま Autotools で行う（変える所を少なくし、Ubuntu 26.04 で起きる問題を切り分けやすくする）。

- `.github/workflows/build.yml`
  - matrix の `os` を `ubuntu-24.04`・`ubuntu-26.04` にする（`ubuntu-22.04` を外し、`ubuntu-26.04` を加える）。
  - 共通のパッケージから `libboost-system-dev` を外す。librcsc の `./bootstrap` に必要な `pkg-config` を加える（librcsc の Phase 6a で `PKG_CHECK_MODULES` を使うようになったため）。
  - Qt WebSockets を入れないジョブ（WebSocket の接続なしのビルドの確認）を、22.04 の Autotools のジョブから 24.04 の Autotools のジョブに移す。22.04 用のパッケージ名（`libqt6websockets6-dev`）の分岐は削除する。
  - Ubuntu 26.04 のパッケージ名が違う場合は、OS ごとに分ける。
  - 使っているコンパイラ、CMake、Qt、Boost のバージョンを表示するステップを加える（librcsc の CI と同じ。結果の記録に使う）。
  - アクションを Node.js 24 で動く版に更新する（`actions/checkout@v7`、`actions/upload-artifact@v7` は librcsc と同じ。`actions/cache` は着手時に版を確かめる）。
  - コメント（Ubuntu 26.04 を外している理由、librcsc の CMake ビルドがメンテナンスされていない旨）を直す。
- 変更をプッシュした後、ユーザが Draft の PR を作る。以後、push のたびに CI が動く。
- CI の結果（各ジョブの環境と成否）を、計画書の実装記録に書く。

### Phase 2: Ubuntu 26.04 で見つかった問題の修正

Phase 1 の CI で見つかった問題を直す。内容は CI の結果を見てから決め、計画書に記録する。予想される問題は「2.5」のとおり。

- コンパイルエラー（GCC 15 の読み込み漏れなど）は、エラーが出たファイルだけでなく、同じ種類の漏れをまとめて直す（CMake のジョブは最初のエラーで止まるため。librcsc と同じ進め方）。
- Qt 6.10 の非推奨の警告も直し、警告0件を保つ。Qt 5.15 と Qt 6.2 でもビルドできる書き方にする（必要なら `QT_VERSION_CHECK` で分ける）。
- Qt5 の qmake が見つからない場合は、`m4/sw2_check_qt.m4` の候補（`/usr/lib/qt5/bin/qmake` など）を見直すか、CI で `QMAKE` を指定するかを、原因を調べてから決める。
- テスト（`soccerwindow2_help`、`gui_smoke` など）が失敗した場合は、原因を調べて直すか、扱いをユーザと決める。
- 手元の Ubuntu 24.04 でも、Qt5・Qt6 × CMake・Autotools のビルドとテストが通ることを確かめる。

### Phase 3: librcsc の Config への対応（CMake）

- ルートの `CMakeLists.txt`
  - まず `find_package(librcsc CONFIG QUIET HINTS ...)` で探す。ヒントには、今の `LIBRCSC_INSTALL_DIR` と環境変数 `LIBRCSC_PREFIX` を使う（`find_package` の `HINTS` で `ENV` が使えるかは実装時に確かめ、使えなければ `$ENV{LIBRCSC_PREFIX}` を渡す）。
  - 見つからなければ、`find_package(Librcsc REQUIRED)`（`cmake/FindLibrcsc.cmake`）で探す。
  - どちらで見つかったか、ライブラリとインクルードディレクトリの場所、（Config の場合は）librcsc のバージョンを構成時に表示する。
  - `LIBRCSC_INSTALL_DIR` の既定値（`~/.local;~/local`）の定義を、`FindLibrcsc.cmake` からルートの `CMakeLists.txt` に移す（Config を探すときにも使うため）。
- `cmake/FindLibrcsc.cmake`: インポートターゲットの名前を `librcsc::rcsc` にする（Config と同じ名前。CMake 3.16 では IMPORTED のターゲットの別名（ALIAS）を作れないため、名前を揃える）。結果の変数の名前は今のまま。
- `src/model/CMakeLists.txt`: `Librcsc::Librcsc` を `librcsc::rcsc` にする。
- `cmake/DistCheck.cmake`: 外側で `librcsc_DIR` が指定されていれば、内側の configure にも引き継ぐかを検討する。
- 注意点（文書に書く）: `LIBRCSC_INSTALL_DIR` の順序で、Config のない場所（Autotools でインストールした librcsc）より、後ろにある Config のある場所が優先される。両方の場所に librcsc がある場合は、`LIBRCSC_INSTALL_DIR` か `librcsc_DIR` で指定する。
- 確かめること
  - 手元の `~/.local`（CMake でインストールした librcsc）が Config で見つかること。インストールした soccerwindow2 の RUNPATH に librcsc の場所が入り、`LD_LIBRARY_PATH` なしで起動できること（一時ホームと offscreen で `--help` を実行する）。
  - `-DCMAKE_DISABLE_FIND_PACKAGE_librcsc=ON` で Config を使わないようにしたとき、`FindLibrcsc.cmake` で見つかり、ビルドとテストが通ること。Autotools でインストールした librcsc（一時ディレクトリにインストールする）でも確かめる。
  - `distcheck` が通ること。

### Phase 4: Autotools での librcsc の探し方

- `configure.ac`: `--with-librcsc` がないときに探す順序を、`$HOME/.local`、`$HOME/local`、`/opt/local`、`/usr/local`、`/usr` にする（CMake・librcsc の既定のインストール先に揃える）。
- 確かめること: `~/.local` と一時的に用意した別の場所の両方に librcsc があるとき、`~/.local` のものが使われること（手元の `~/local` には触らず、`HOME` を一時ディレクトリにして確かめる）。

### Phase 5: CI での librcsc のビルドの変更

「3. 決定事項」の2により、soccerwindow2 と同じビルドシステムで librcsc をビルドする。

- CMake のジョブ: librcsc を CMake でビルドし（`cmake-helper.sh` を使い、テストは作らない `-DBUILD_TESTING=OFF`）、`~/local` にインストールする。インストール先は今と同じ `~/local` にする（ランナーの `~/.local` にはほかのファイルがある可能性があり、キャッシュに混ぜないため。soccerwindow2 は `~/local` も既定で探す）。
- Autotools のジョブ: 今のまま Autotools でビルドする。
- キャッシュのキーに librcsc のビルド方法を加える（`librcsc-<os>-<build>-<リビジョン>`）。
- CMake のジョブで、librcsc が Config で見つかったことを確かめる（構成の表示か `CMakeCache.txt` の `librcsc_DIR` を調べる）。
- CMake のジョブの最後に、`-DCMAKE_DISABLE_FIND_PACKAGE_librcsc=ON` で構成し直してビルドとテストを行い、予備の `FindLibrcsc.cmake` でも使えることを確かめる（インクルードディレクトリが同じなので、リンクのやり直しだけで済む見込み）。
- ワークフローのコメントを直す。

### Phase 6: Boost への依存の除去

- `src/model/csv_logger.h`: `boost::lexical_cast< std::string >( data )` を `std::ostringstream` などに置き換える（浮動小数点数の桁数が変わらないよう、`std::numeric_limits<T>::max_digits10` の精度にするなど、`lexical_cast` と同じ結果になる書き方を実装時に確かめる）。
- CMake: `find_package(Boost ...)`、CMP0167 の設定、`Boost::headers` へのリンクを削除する。
- Autotools: `AX_BOOST_BASE` と `$BOOST_CPPFLAGS` を削除し、`m4/ax_boost_base.m4` を削除する（ほかに使っていないことを確かめる）。
- `soccerwindow2.spec.in`: `BuildRequires: boost-devel` を削除する。あわせて、librcsc の最低バージョン（`>= 1.3.0`）を見直す。
- CI: soccerwindow2 のためには Boost が要らなくなるが、librcsc のビルドに `libboost-dev` が要るので、パッケージの一覧には残す（コメントで librcsc のためと分かるようにする）。
